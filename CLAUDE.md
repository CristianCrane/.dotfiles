# Dotfiles

The NixOS-on-WSL2 system (a flake, applied with `rebuild`) and Claude Code's own config, `home/.claude`, which `home.nix` (`claudeSettings`) links into `~/.claude`.

- **Changes reach `main` by PR, and the user merges them** (2026-11-19: several agents now add to this repo), but for a process batch (`docs/process.md`, Landing). GitHub's ruleset "main: changes by pull request" holds `main`: every change by a pull request (0 approvals, since agents open PRs as the user), no force push or deletion, no bypass. Build in a `git worktree` off `origin/main` under the change skill and open the PR; the survey gate turns down edits on `main` in any checkout whose origin is on GitHub, `~/.dotfiles` included. Only the user merges: review-gate turns down `gh pr merge` here unless a message the user typed in this session asks to merge that PR's number. CI (`.github/workflows/hooks.yml`) runs the hook tests on each PR. The user's own saves into `~/.dotfiles` (`/model`, `/effort`, a plugin toggle) aren't tool edits: an agent asked to lands them from a worktree off `origin/main` with the changed files copied in, as a PR. `~/.dotfiles` catches up with `origin/main` at every session start (`home/.claude/hooks/catch-up.mjs` says how, and when a change waits for the user's `rebuild`), so a merged PR's `home/.claude` is live from the next session.
- **Claude Code's config** (the global CLAUDE.md, `settings.json` with its `enabledPlugins`, hooks, agents, skills) is changed here and committed, not through installers that write around it.
- **The links point at `~/.dotfiles`'s working tree,** so whatever it has checked out runs in every session the moment it's saved: keep it on `main`. Try a hook change first in a `git worktree` of this repo, and live in one session by registering the worktree's copy in a project's `.claude/settings.local.json` (wait a few seconds before starting agents; remove it after), then open its PR.
- **Hook tests:** every hook but stale-copy has cases in `home/.claude/hooks/change-hooks.test.mjs`; a change to one (or to lib.mjs, copy.mjs, sync.mjs) adds its cases there and runs them (`node --test 'home/.claude/hooks/*.test.mjs'`). stale-copy is fed its hook inputs by hand.
- **A new hook, gate or command** starts from how often its case has happened (with dates) and the simplest thing that would hold (a setting, a timeout, a line in a hook that exists). It says what it costs each session and agents working at once, and it adds nothing unasked: a branch that outgrows its ask stops and asks (.dotfiles#23 grew from an alias into reviewer-gate rewrites and was paused, 2026-11-10).
- **A hook or script that deletes things** plans, before its first review, for being killed partway and for two runs at once (Claude Code kills an async hook at its timeout; SessionStart fires on startup, resume, clear, compact and fork): a lock, touching only what this run judged, and every cut-short step safe for the next run.
- **A hook that prints at session start** is tried on a real, busy repo before it lands. What only the main session needs goes in `home/.claude/hooks/main-session.md`, which `main-session.mjs` prints at session start: agents never get SessionStart output.
- **Before naming a new skill, agent or command,** search the installed plugins (`~/.claude/plugins/cache`) for the name.
